# Does moving the fallback observation into a service earn its cost?

Prospective paired, owner-run experiment. Publish this protocol and freeze the task bytes and implementation before opening any outcomes. Stage README releases from eight different public projects (Click, Flask, HTTPX, Requests, Jinja, ItsDangerous, Starlette and Packaging). Pin each upstream revision and hash its actual README bytes. Use isolated temporary storage and an identical grant for one versioned destination per task. No change is sent upstream.

Cross all eight lineages with intended bytes committed, no commit, or different bytes committed, primary status available or unavailable, and fallback sharing primary availability or reading the released file through a separately running observer. These are interventions with equal weight, not estimates of failure frequency. Primary status reports the observed digest or an absent object. Failure returns no observation. An exact digest can verify release. Absence or different bytes leaves the intended release unresolved. The evaluator reads the filesystem after the decision and separately scores a false closure. The sender gets the same ambiguous acknowledgement for all releases.

Compare a conventional caller that checks primary status then fetches fallback on failure with a service that performs the identical checks and returns the observation to the caller. Both get the same observations, one write, at most two status reads, no rewrite, and the same recovery budget. Include a primary-only ablation to distinguish extra evidence from where the check runs. Rotate arm order across cells and use a new destination state per arm. Both servers and the client run on one host. Independent observation means separate read process and availability control, with a shared host and artifact store.

Report verified completions, false closures, unresolved requests, caller and total status requests, status body bytes in both directions across every hop, and elapsed time from ambiguous acknowledgement to decision. Record time to verified closure only for verified cases. Response timing includes local scheduling and is descriptive. Publish every case, its immutable input, and all failures. Keep zero false closures as a hard requirement. Recommend the extra observation only in a stratum where it adds verified completions without false closure. Prefer moving it into a service only if it adds verified completions at equal safety or ties while using no more total requests or body bytes and improves at least one. Otherwise prefer direct checking on this workload. Human labor, TLS, wide-area loss and independently operated storage remain unmeasured.
